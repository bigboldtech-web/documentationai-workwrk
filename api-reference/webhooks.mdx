A webhook subscription is an HTTPS endpoint of yours plus a list of events. When one of those events happens in your organization, WorkwrK POSTs a signed JSON payload to the endpoint, records the attempt, and retries on failure.

Subscriptions are per organization, and every delivery is signed so you can prove it came from us.

<Callout kind="alert" collapsed="false">
  **There is no webhook screen in the app yet.** Subscriptions are created, listed, given a new secret and deleted through `/api/webhooks`, and that endpoint authenticates against a signed-in administrator's dashboard session, not an API key. Until a UI ships, registering a webhook means calling it with an admin session cookie. Everything on this page about payloads, signing and retries is live and working; only the management surface is rough.
</Callout>

## Registering a subscription

`POST https://workwrk.com/api/webhooks` with `url` and `events`. The caller must be signed in as the workspace's **Owner** or an **Admin**; on production the session cookie is `__Secure-next-auth.session-token`.

<CodeGroup show-lines="true" tabs={["Request","Response"]}>
  ```bash Request
  curl -X POST https://workwrk.com/api/webhooks \
    -H "Content-Type: application/json" \
    -H "Cookie: __Secure-next-auth.session-token=YOUR_ADMIN_SESSION_COOKIE" \
    -d '{
      "url": "https://hooks.acme.com/workwrk",
      "events": ["kudos.created", "kpi.recorded"]
    }'
  ```

  ```json Response
  {
    "id": "clx9m4p2r0001t7028kd5w1qz",
    "url": "https://hooks.acme.com/workwrk",
    "events": ["kudos.created", "kpi.recorded"],
    "status": "ACTIVE",
    "secretPrefix": "whsec_9fK3",
    "createdAt": "2026-08-18T14:22:51.008Z",
    "secret": "whsec_9fK3xQ7mZp2LvN8hJc4bY6dS1gA0eR5tW3uX9yB7cD1",
    "signing": "secret",
    "message": "This is the only time we'll show the webhook signing secret. Store it now. Each delivery carries X-Workwrk-Signature: t=<timestamp>,v1=<signature>. To check one, compute HMAC-SHA256 with this secret as the key over the timestamp, a full stop and the raw request body (<timestamp>.<body>), as lowercase hex, and compare it with v1 in constant time. Refuse a timestamp more than five minutes old."
  }
  ```
</CodeGroup>

Notes on the request:

- **The secret is returned once.** It is the key every delivery is signed with. WorkwrK keeps it encrypted to sign with and never shows it again. Lose it and rotate the secret (below) to get a new one.
- **`events`****&#x20;is optional.** Omit it and the subscription is created with `["*"]`, which receives everything.
- **An event name nothing sends is refused.** Every name is checked against the list below, and a name that is not on it gets a `400` naming it, with nothing saved. A typo therefore fails out loud instead of making a subscription narrower than you intended.
- **The URL check accepts&#x20;****`http://`****&#x20;as well as&#x20;****`https://`****.** Use https regardless; the payload contains real people data.

The other operations:

```bash
# List subscriptions, their health, and the accepted event names
curl https://workwrk.com/api/webhooks \
  -H "Cookie: __Secure-next-auth.session-token=YOUR_ADMIN_SESSION_COOKIE"

# Give a subscription a new secret, shown once; the old one stops signing at once
curl -X PATCH https://workwrk.com/api/webhooks \
  -H "Content-Type: application/json" \
  -H "Cookie: __Secure-next-auth.session-token=YOUR_ADMIN_SESSION_COOKIE" \
  -d '{ "id": "clx9m4p2r0001t7028kd5w1qz", "rotateSecret": true }'

# Delete a subscription and its delivery history
curl -X DELETE "https://workwrk.com/api/webhooks?id=clx9m4p2r0001t7028kd5w1qz" \
  -H "Cookie: __Secure-next-auth.session-token=YOUR_ADMIN_SESSION_COOKIE"
```

`GET` returns each subscription with `status`, `failureCount`, `lastSuccessAt`, `lastFailureAt` and a delivery count, plus a `validEvents` array. Each subscription also carries `signing`, which says which key signs its deliveries (see [Verifying the signature](#verifying-the-signature)), and `unsentEvents`, any names it holds from before that nothing sends. That listing is your only observability today: there is no delivery-log screen.

`PATCH` with `rotateSecret: true` is the only update: it returns a new secret, once, and the old one stops signing at once, so update your receiver straight away. To change a URL or an event list, delete the subscription and create a new one, which mints a new secret.

## Events

There are six events. Name any of them when you register, or `*` for all of them.

| Event | Fires when |
| --- | --- |
| `*` | Every event below. |
| `kudos.created` | Every new kudos. |
| `kpi.recorded` | A KPI reading is logged through the API (`POST /kpi-records`) or an integration. Not for a number recorded on a person's record in the app. |
| `task.created` | A task is added to a List in the app, made through the API (`POST /tasks`) or an integration, made by an automation's **Create a task** step, or made by Ask AI or an AI teammate. Not for copies (a task, List or Space duplicated), tasks from a template, the next task of a repeating task, tasks an SOP adds, form responses, meeting action items, quick add from My work, workflows or imports. |
| `task.status_changed` | A task's status changes: one task edited in the app or by an AI teammate, a bulk edit, or an automation step. Carries `previousStatus`. |
| `task.assignee_changed` | A task's main assignee changes, from the same places. Carries `previousAssigneeId`. |
| `task.field_changed` | Once for each field a change touches (title, priority, dates and the List's own fields): one task edited in the app or by an AI teammate, a bulk edit, an AI field fill, or an automation's **Set a field** step. One edit of one task fires it for at most 20 fields. |

The older names (`task.escalated`, `task.completed`, `review.created`, `review.completed`, `sop.published`, `sop.updated`, `okr.created` and `okr.updated`) are no longer accepted, because nothing sends them. A subscription made before keeps the names it holds, and `GET` lists them under `unsentEvents`, so you can see why that part of it stays quiet.

## The payload

```json
{
  "id": "clx9m4p2r0009t702f1h6k8ab",
  "event": "kudos.created",
  "createdAt": "2026-08-18T14:23:07.412Z",
  "data": {
    "id": "clx9m4p2r0007t702j8v3n5xy",
    "message": "Turned the escalation around in a single afternoon.",
    "companyValue": "Ownership",
    "giverId": "clx8f2n0k0005s601j4k7m2np",
    "receiverId": "clx8f2n0k0001s6019vq3h7bd",
    "createdAt": "2026-08-18T14:23:07.402Z"
  }
}
```

`data` is the record exactly as the originating endpoint returned it. A `kpi.recorded` payload carries the KPI record with its computed `score`; a `task.created` payload carries the task. There is no schema envelope beyond the four top-level keys.

Every request carries these headers:

| Header                | Example                     | Purpose                                                            |
| --------------------- | --------------------------- | ------------------------------------------------------------------ |
| `X-Workwrk-Event`     | `kudos.created`             | Route to the right handler, especially on a wildcard subscription. |
| `X-Workwrk-Delivery`  | `clx9m4p2r0009t702f1h6k8ab` | Stable delivery id. Use this for de-duplication.                   |
| `X-Workwrk-Timestamp` | `1755527387`                | Unix seconds. Part of the signed string.                           |
| `X-Workwrk-Signature` | `t=1755527387,v1=4b9f...`   | HMAC of the payload. See below.                                    |
| `User-Agent`          | `workwrk-webhooks/1.0`      | Identifies the sender.                                             |

<Callout kind="alert" collapsed="false">
  **De-duplicate on the delivery id.** The body's `id` is the delivery's id, the same value as the `X-Workwrk-Delivery` header, and every try of one delivery carries the same `id`. Deliveries are sent at least once, so one you already have can arrive again: keep the ids you have processed and drop a repeat.
</Callout>

## Verifying the signature

`X-Workwrk-Signature` has the form `t=<timestamp>,v1=<hex>`. The `v1` value is an HMAC-SHA256 over the string `<timestamp>.<raw request body>`.

<Callout kind="alert" collapsed="false">
  **The HMAC key is your secret itself**, the `whsec_...` value shown once when the subscription was made or its secret rotated. An older subscription may still sign with the SHA-256 of its secret, as lowercase hex, as the key. `GET /api/webhooks` says which in `signing`: `secret` or `legacy_hash`. Rotating its secret moves it to the secret itself.
</Callout>

```js
const crypto = require("crypto");

// The whsec_... value shown once when the subscription was made or its secret rotated.
const SECRET = process.env.WORKWRK_WEBHOOK_SECRET;

// WorkwrK signs with that secret. Only a subscription whose `signing` is
// legacy_hash signs with its SHA-256 instead:
// crypto.createHash("sha256").update(SECRET).digest("hex")
const SIGNING_KEY = SECRET;

// Refuse a timestamp more than five minutes old.
const TOLERANCE_SECONDS = 5 * 60;

function verify(rawBody, signatureHeader) {
  const parts = Object.fromEntries(
    signatureHeader.split(",").map((p) => {
      const i = p.indexOf("=");
      return [p.slice(0, i), p.slice(i + 1)];
    }),
  );

  const age = Math.floor(Date.now() / 1000) - Number(parts.t);
  if (Number.isNaN(age) || age > TOLERANCE_SECONDS) return false;

  const expected = crypto
    .createHmac("sha256", SIGNING_KEY)
    .update(`${parts.t}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "utf8");
  const b = Buffer.from(parts.v1 ?? "", "utf8");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

Wire it up against the **raw** body, before any JSON parsing. Re-serializing the parsed object changes the bytes and breaks the signature:

```js
app.post(
  "/workwrk",
  express.raw({ type: "application/json" }),
  (req, res) => {
    if (!verify(req.body.toString("utf8"), req.headers["x-workwrk-signature"])) {
      return res.status(401).send("bad signature");
    }

    // Acknowledge first, work afterwards. The sender waits 10 seconds.
    res.status(200).send("ok");

    const delivery = req.headers["x-workwrk-delivery"];
    const event = JSON.parse(req.body.toString("utf8"));
    enqueue(delivery, event);
  },
);
```

The timestamp is signed, and every try is signed afresh with the time it is sent, so a retry that arrives hours after the event still carries a current timestamp. Refuse one more than five minutes old, as the code above does.

## Delivery, retries and auto-pause

<Steps>
  <Step title="First attempt" icon="send" title-type="p">
    The POST is fired as soon as the event happens, with a 10-second timeout. Any `2xx` marks the delivery **delivered** and resets the subscription's failure counter to zero. Anything else, including a timeout or a connection error, counts as a failure.
  </Step>

  <Step title="Retries" icon="rotate-cw" title-type="p">
    A failed delivery is queued with an exponential backoff: 1 minute, then 2, 4, 8, 16, 32, and capped at 1 hour. A retry job runs every 5 minutes and processes up to 100 due deliveries per run, so the real gap is the backoff rounded up to the next run.
  </Step>

  <Step title="Giving up" icon="circle-x" title-type="p">
    After 8 attempts the delivery is marked **failed** and is never retried again. There is no way to replay it, so a subscriber that is down for the whole retry window loses those events permanently.
  </Step>

  <Step title="Auto-pause" icon="pause" title-type="p">
    The subscription keeps a rolling failure count that increments on every failed delivery and resets to zero on any success. At 10 failures the subscription is set to **paused**, and paused subscriptions receive nothing at all.
  </Step>
</Steps>

<Callout kind="alert" collapsed="false">
  **A paused subscription cannot be resumed.** The only update, rotating the secret, does not resume it, and there is no UI control, so the only route back is to delete the subscription and register a new one, which issues a new signing secret. If your endpoint is going down for maintenance, keep in mind that ten failed deliveries is enough to pause it.
</Callout>

Guarantees, stated plainly:

- **At least once, not exactly once.** If your endpoint processes a delivery but responds slowly enough to time out, you will get it again, and a delivery whose answer was never recorded is sent again. Every try carries the same `id` in its body, the same as `X-Workwrk-Delivery`, so de-duplicating on it is not optional.
- **No ordering.** Deliveries to different subscriptions fan out in parallel, and retries interleave with fresh events. Do not assume a `task.created` arrives before a later `task.status_changed` for the same task.
- **No delivery on paused or deleted subscriptions.** Only subscriptions in the active state are selected when an event fires.
- **Held, not lost, when a secret can't be opened.** A subscription whose `signing` is `unreadable` has a secret the server can't open right now, so nothing is sent to it. Its deliveries are held and tried again every 15 minutes until the secret can be opened or is rotated.
- **Deleting a subscription deletes its delivery history** along with it.

## Building a good receiver

<Columns cols="2">
  <Card title="Verify before you trust" icon="shield-check" horizontal="false">
    Check the signature on the raw body and return `401` if it fails. Nothing else about the request proves it came from WorkwrK.
  </Card>

  <Card title="Acknowledge in under 10 seconds" icon="timer" horizontal="false">
    Return `2xx` as soon as you have the payload safely queued. Do the real work off the request path.
  </Card>

  <Card title="Key on the delivery id" icon="fingerprint" horizontal="false">
    Record the body's `id`, the same as `X-Workwrk-Delivery`, and drop repeats. Retries are normal, not exceptional.
  </Card>

  <Card title="Filter on the event header" icon="filter" horizontal="false">
    Name only the events you handle. On a wildcard subscription, branch on `X-Workwrk-Event` and ignore the rest.
  </Card>
</Columns>

If you only need to react to a handful of events and cannot register a subscription yet, polling the list endpoints is the fallback. Read [Pagination](/api-reference/pagination) for the sort orders that make polling workable, and [Rate limits](/api-reference/rate-limits) before you pick an interval.
