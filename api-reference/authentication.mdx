Every call to `https://workwrk.com/api/v1` is authenticated with a workspace API key sent as a bearer token. Keys are made in the app by an Owner or Admin, shown exactly once, and stored only as a hash.

## Create a key

<Steps>
  <Step title="Open API & webhooks" icon="settings">
    In the app, open Workspace settings from your avatar menu. Under **Security & data**, choose **API & webhooks**. The direct path is `/settings/api`.

    Owners and Admins manage keys.
  </Step>

  <Step title="Generate a key" icon="key">
    Choose **Generate key**. The **Generate an API key** dialog asks for two things:

    - **Name**: where the key is used, so you know what breaks if it is revoked.
    - **Scopes**, as three choices: **Read** ("Read workspace data through the API."), **Write** ("Create and update records.") and **Admin** ("Everything Write does, and inviting people. Keys and webhooks are managed only here, never with a key. Give it sparingly."). **Read** is chosen to start.

    Pick the narrowest set that does the job. You can choose more than one. **Scopes cannot be changed after a key is made. Make a new key instead.**
  </Step>

  <Step title="Copy the secret now" icon="clipboard-copy">
    **Copy your new key** shows the full key once, with the warning "This is the only time", the key's name, then "is shown. Store it somewhere safe now." Choose **Done, I have saved it** when you have.

    That is literal. Close the dialog without copying and the key is unrecoverable; your only option is to revoke it and make another.
  </Step>
</Steps>

Back on the list you see the key as a row with its **Name**, **Prefix**, **Scopes**, **Rate limit**, **Last used** and **Created by**. Open a row to see its details and change its rate limits. **Show revoked keys** brings revoked ones back into the list.

## Key format

A key looks like this:

```
wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e
```

It is the literal prefix `wk_live_` followed by a 32-character random token (24 bytes of cryptographic randomness, base64url-encoded).

What the server keeps:

| Stored | Value |
| --- | --- |
| A hash | The SHA-256 digest of the full key. This is what a request is matched against. |
| The prefix | The first 12 characters, that is `wk_live_` plus the first four characters of the token. Used for display and to help you identify a key in the list. |
| Plaintext | Nothing. It is never written to the database. |

## Sending the key

Put it in the `Authorization` header as a bearer token:

<CodeGroup>
```bash curl
curl "https://workwrk.com/api/v1/tasks?limit=5" \
  -H "Authorization: Bearer wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e"
```

```bash POST with a body
curl -X POST https://workwrk.com/api/v1/kpi-records \
  -H "Authorization: Bearer wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e" \
  -H "Content-Type: application/json" \
  -d '{
    "kpiId": "clx8f2n0k0011s601t4v8y2qw",
    "userId": "clx8f2n0k0001s6019vq3h7bd",
    "period": "2026-09",
    "actualValue": 47
  }'
```
</CodeGroup>

The scheme name is matched case-insensitively, so `bearer` works as well as `Bearer`. The token itself must start with `wk_live_`; anything else is rejected before a database lookup happens.

There is no support for the key in a query string, a cookie, or a custom header. Bearer only.

## Scopes

Three scopes exist: `READ`, `WRITE` and `ADMIN`. A key carries one or more of them. When an endpoint asks for a scope, the check resolves like this:

| Endpoint requires | Satisfied by |
| --- | --- |
| `READ` | `READ`, `WRITE`, or `ADMIN` |
| `WRITE` | `WRITE` or `ADMIN` |
| `ADMIN` | `ADMIN` |

Which scope each endpoint needs:

| Endpoint | Scope |
| --- | --- |
| Every `GET` | `READ` |
| `POST /kras`, `/kpis`, `/kpi-records`, `/kudos`, `/tasks` | `WRITE` |
| `POST /people` (invite a person) | `ADMIN` |

Three consequences worth internalizing:

- A **WRITE**-only key can also read. `WRITE` satisfies a `READ` requirement, so you do not need both for a read-and-write integration.
- **Inviting people needs ADMIN.** The `WRITE` check runs first, so a READ-only key gets `403` with `This key needs "WRITE" scope. It has: READ.`, and a key with `WRITE` but not `ADMIN` gets `403` with `Inviting people needs a key with the "ADMIN" scope.` Treat an ADMIN key as the most sensitive thing you hold: it satisfies every check.
- **No key manages keys or webhooks.** `/api/keys` and `/api/webhooks` take a signed-in Owner's or Admin's session, never an API key, as the **Admin** description in the dialog says.
- **A key is not tied to the person who made it.** It reads and changes what its scopes allow across the whole workspace, whoever made it, and it keeps working if that person leaves. Revoke it when its job ends.

The scope each operation needs is also written into the OpenAPI spec, so your client will show it.

## When authentication fails

A rejected request returns HTTP `401` and a JSON body with a single `error` field:

<CodeGroup>
```bash Request
curl -i https://workwrk.com/api/v1/people \
  -H "Authorization: Bearer wk_live_thiskeywasrevokedlastweek000000"
```

```json Response
{
  "error": "API key has been revoked"
}
```
</CodeGroup>

The `401` messages you can get, and what each one means:

| Message | Cause |
| --- | --- |
| `Invalid API key format` | The bearer token does not start with `wk_live_`. Usually a truncated copy or the wrong secret entirely. |
| `Invalid API key` | Correctly formatted, but no key hashes to it. A single wrong character produces this. |
| `API key has been revoked` | The key existed and was revoked. Make a new one. |
| `Missing or invalid credentials. Send Authorization: Bearer <key>.` | No `Authorization: Bearer` header at all, and no signed-in session either. |

A key that is valid but too narrow returns `403` instead, with the scopes it does have spelled out:

```json
{
  "error": "This key needs \"WRITE\" scope. It has: READ."
}
```

A key for a suspended or cancelled workspace also returns `403`: `This workspace is suspended. Please contact WorkwrK support.`

Full status-code reference is in [Errors](/api-reference/errors).

## Revoking a key

Open the key and choose **Revoke**. **Revoke this key?** asks first, and **Revoke key** confirms.

Revocation takes effect on the very next request. The row stays, marked revoked, under **Show revoked keys**, so you keep the record, and both making and revoking a key are written to the audit log.

There is no rotation flow. To rotate, generate the replacement key first, deploy it, then revoke the old one.

## Knowing whether a key is still in use

Each key records when it was last used, the address it was last used from, and how many requests it has made. The **Last used** column shows when, and opening the row shows the request count under **Requests**. The address is recorded, but the page does not show it. That is how you check a key is genuinely dead before revoking it.

## Signing in instead of a key

If you call a `/api/v1` endpoint from a browser tab where you are signed in to WorkwrK, and you send no `Authorization` header, the request uses your session instead. **This works only for the workspace's Owner and Admins.** Anyone else gets `403`: `The API takes an API key (Authorization: Bearer <key>). A signed-in session works only for the workspace's Owner and Admins.` Your role is read fresh on every request, so taking someone's Admin role away takes the API away at once.

A session works as all three scopes. It exists so an Owner or Admin can try an endpoint from the address bar while exploring. Do not build on it: the rate limiter does not apply to that path, sessions expire, and nothing about it is a stable integration contract. Real integrations use a key.

<Callout kind="tip">
  Store the key in your secret manager or environment, never in source control. If a key leaks, revoking it in the app is instant and total.
</Callout>
